删原文件，或重建索引之后，历史会话里的图片 chunk 还能否打开

对照 WeKnora、RAGFlow、Dify、FastGPT、LightRAG、AnythingLLM、Cognee。只看文件生命周期和历史引用，不看技能与记忆。

这些系统把引用文字抄进会话记录，图片字节留在索引或对象存储里。历史会话再打开时，文字从记录里读，图片按当时的地址再去取。删原文件会把索引和图片对象一起清掉，文字还在，图片打不开。重建索引通常留下原文件、换掉 chunk；图片多半也换掉或删掉，旧地址打不开。FastGPT 是例外：重训把图片清掉被当成缺陷修过。

没有一家把「已经被某条消息引用过的图片」复制到会话自己的路径，或做到引用计数之后再删。

文字还在 能打开 打不开 不一定，看清理是否打中 没有这种图片 chunk

调研截止 2026-09-29。依据是公开仓库当前主分支、issue 和文档，不是把这些产品跑一遍。

删除原文件之后

原文件、chunk、从文档里抽出的图片，都按文档 id 清掉。会话记录不改。所以历史里看得到当时的文字，点图片或按旧 chunk id 打开会失败。

WeKnora 删掉 还在消息 JSON 里 导出图删掉，URL 还在消息里 打不开 按 chunk id 查是 404，图片链接也 404
RAGFlow 删掉 还在会话 reference 里 按 chunk 去对象存储删除 打不开 /v1/document/image/ 取的是活对象
Dify 删掉 还在 retriever_resources.content 抽出的图和附件都删 打不开 旧 segment 没了，原文签名也找不到文件
FastGPT 集合删除时清掉 聊天记录里的 q/a 还在 clearCollectionImages，受 ALLOW_IMAGE_DELETE 控制 详情打不开 点引用会去读还活着的数据行

重建索引之后

原文件一般留下。chunk id 换新。历史文字仍是当时抄下来的那一份。图片是活指针：对象被换掉或删掉，旧会话就打不开。RAGFlow 的清理顺序经常漏删图片对象，所以旧图有时还能打开，这是漏清，不是为历史保留。

系统 原文件 历史文字 旧图片 chunk 旧引用还能打开吗
WeKnora 留下，预览仍可用 还在 导出图删除后按新 uuid 重写 图片打不开 悬停按旧 chunk id 查询 404。原文预览不是那张引用图
RAGFlow 留下 还在 打算删，但先删了索引再找图，经常找不到对象 对象还在就能打开，删掉就打不开
Dify 留下，每次打开重新签名 还在 更新任务删的是 segment 和向量，没有删图片对象 原文能打开；旧 segment 打不开。正文里的图片文件这次清理没覆盖，可能仍能打开
FastGPT 集合还在 q/a 还在 4.9.8 起重训丢图被修掉，图应留下 旧数据 id 的详情打不开；图片对象按修复目标应仍能打开
LightRAG 同名文件必须先删再传，等于删了再索引 无引用快照 旧 chunk、向量、独占图节点删除 没有可打开的旧图片 chunk
AnythingLLM 重嵌用不删文档库原件 聊天记录还在 向量按 docId 换掉，无图片 chunk 引用 不能打开旧的解析图
Cognee 再次 cognify 前若 forget，原文件默认删除 无引用快照 图和向量按 data_id 清 没有可打开的旧图片 chunk

文件生命周期和历史引用怎么挂在一起

文字快照，图片活指针

WeKnora、RAGFlow、Dify。回答时把 chunk 正文写进消息。图片只存 id 或 URL。删文档或重建时清索引对象，不回写历史消息。

问答快照，详情读活数据

FastGPT。列表上的问题和答案留在聊天记录。点开引用、看图，都回到知识库当前的数据和图。重训换 id 后详情失败；图片按资产保留，丢图算故障。

索引和文件同生同灭

LightRAG、Cognee。没有「这条消息引用了哪张解析图」的账。删文档就是删索引。AnythingLLM 的聊天记录另存，但也不留解析图。

三家都用文档 id 当清理键：WeKnora 是 knowledge_id，RAGFlow 是 doc_id，Dify 是 document_id，FastGPT 是 collectionId。清理顺序都是先收齐图片地址，再删 chunk，再删对象。失败只记日志，不回滚已经删掉的数据库行。会话表不在这条链上。

每家怎么管

WeKnora

索引在 Postgres（chunk、向量、BM25）和可选 Neo4j。原文件键是 {tenant}/{knowledge}/{uuid}.ext。抽出的图在 {tenant}/exports/{uuid}.ext，不挂在 knowledge 目录下。

  • 重建：reparseKnowledge 先 cleanupKnowledgeResources。删向量、chunk、图数据库命名空间，并 deleteExtractedImages。原文件 FilePath 不动。新 chunk 用新的 uuid。
  • 删除：先删知识行，再删原文件和导出图（2026-07 的删除顺序修正）。chunk、向量、图一并清。文件删失败会留下孤儿，这是他们接受的失败方式。
  • 历史：knowledge_references 是整段检索结果的 JSON，含正文和 image_info。重建和删除都不改它。
  • 打开方式：悬停用 GET /chunks/by-id/:id 读活 chunk，旧 id 404。点开抽屉读的是消息里的文字。图片请求的是 exports 上的旧 URL。
RAGFlow

原文件、chunk 缩略图都在按知识库分桶的对象存储。会话表另存 reference。

  • 重建：reset_document_for_reparse 把进度打回未开始，按 doc_id 删索引 chunk，再调用 delete_chunk_images。后者要先搜到 chunk，再用 chunk id 当对象键删除。索引已经删空时，这一步经常删不到图。
  • 删除文档：remove_document 在 chunk 还在时删图片对象和缩略图，再删任务和索引。原文件一起删。删除失败记日志，继续。
  • 历史：打开会话只是把已存字段整理成 content 和 image_id。官方把 img_id 写成「该 chunk 的快照 id」，指的是对象存储里的页图，不是把图片字节写进会话。
  • 打开方式：GET /v1/document/image/{知识库id}-{对象名} 现取 JPEG。对象还在就能开，对象没了就失败。正文不受影响。
Dify

消息元数据存 retriever_resources：dataset、document、segment、分数、content。图片是 segment 正文里的 upload file。

  • 重建：document_indexing_update_task 按 index_node_id 清向量和关键词，成功后删掉旧 DocumentSegment，再跑一遍索引。这段代码不删原上传文件，也不调用删图片对象的逻辑。
  • 删除：文档行先硬删。clean_document_task / batch_clean_document_task 再删向量、segment、从正文解析出的图片、附件和原文件。storage.delete 失败只记日志。
  • 历史：content 留在消息上。segment_id 在重建后指向已经不存在的行。「查看原文」每次读取重新签发：上传文件是短时签名，网页是原 URL。issue #21068 里维护者说明，旧会话每次打开都会重新签名。
  • 打开方式：文档还在时原文能开。文档删了，原文和图都打不开。重建后旧 segment 打不开；图片对象因为更新任务没删，可能仍能打开。
FastGPT

聊天记录和知识库数据分表。引用列表保存收瘦后的 quote，其中 q/a 保留（PR #6977 有断言）。

  • 重建：重训会换掉该集合下的数据行，旧 data id 作废。issue #4431：大文件重分块给图片写了 expiredTime，超时任务把图删了。PR #4757 把这件事修掉，4.9.8 的说明是「重训时过期图片索引没清干净导致丢图」。修复目标是重训后图片还在。
  • 删除集合：删训练数据、数据文本、数据行，并 clearCollectionImages。关联图还要看 ALLOW_IMAGE_DELETE（讨论 #5035）。
  • 历史：列表上的问答文字还在。点开引用走 getQuoteData，按当前数据行读取。行没了，详情失败。
  • 聊天里用户上传的文件在 GridFS，大约 7 天过期，和知识库图片不是一条生命周期。
LightRAG、AnythingLLM、Cognee
  • LightRAG：同名文件不能直接覆盖，必须先删再传。adelete_by_doc_id 删该文档的 chunk 和向量；只属于该文档的图节点删除，多文档共用的实体只改 source_id。没有把图片 chunk 挂到会话上。
  • AnythingLLM：从工作区移除文档时按 docId 删向量、workspace_documents 和 document_vectors。聊天记录留下，用于导出，不作为记忆。引用是来源信息。文档库里的原件和「移出工作区」不是同一步。/img 生成的图会跟聊天存，那是生图，不是解析出的 chunk 图。
  • Cognee：forget(data_id) 清关系记录、图和向量。原文件默认删除，memory_only=true 才留。共用图节点要等最后一个引用消失。没有会话级引用，也没有图片留给历史。

若要让历史继续看见那张图

索引里的导出图可以换、可以删，这和 RAGFlow 删文档、Dify 删文档、WeKnora 重建时的清理是同一类账，用来避免对象堆积。历史打不开，是因为图片地址写进了消息，字节没有跟着消息走。

要同时满足「索引可重建」和「旧会话还能看见图」，图片得有第二份归属：写进消息时复制到会话自己的路径，或者给对象做引用计数，直到没有任何消息再指向它才删。上面七家里没有一家做成这一点。FastGPT 只是把重训误删知识库图片修掉了，旧的数据 id 仍然打不开。

主要依据：WeKnora knowledge_process.go 的 reparseKnowledge / cleanupKnowledgeResources，PR #880 与 2026-07 删除顺序修正；RAGFlow reset_document_for_reparse（提交 0f6f7b3c）、delete_chunk_images、GET /image/<image_id>；Dify document_indexing_update_task、clean_document_task、PR #27600、issue #21068；FastGPT PR #6977、issue #4431、PR #4757、讨论 #5035。LightRAG、AnythingLLM、Cognee 没有读到会话图片引用的实现，表中记为没有这种对象。
