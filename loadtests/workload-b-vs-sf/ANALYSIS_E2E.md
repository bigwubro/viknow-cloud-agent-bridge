# 自建四卡：并发升高后端到端时延为什么变长

依据：2026-09-18 06:47–07:28 UTC，工作负载与硅基流动、Neolink 对照同一套——约 3.3 万输入 token、184 个输出 token，各请求共用一段长上下文、仅末尾不同；思考模式关闭。自建接口 `127.0.0.1:8500`，模型 `Qwen/Qwen3.6-35B-A3B-FP8`。当时启动参数未改，与现网 `vllm-vlm` 一致。

数字来自各档 `finished.json` 与窗口内每 5 秒抓取的 Prometheus。成功指出口返回 HTTP 200。本文只解释时延，不改服务。

## 结论

并发从 1 提到 80，中位时延从 **3.1 秒升到 50.2 秒**，并不是请求在门口排长队。门口排队最多只占中位时延的 **3.4%**。变慢发生在请求已经进入计算槽位之后：四张卡各自用 **16384 token** 的一步预算，同时做「新请求的长预填充」和「已在生成的请求再吐一个词」。新请求每次仍要现场计算约 **1.8–2.7 万** token（共享段大约命中 39%，独特尾巴约 1.3 万算不中）。一步预算几乎被一次预填充占满，同卡上其它请求这一步就轮空。

结果是：在算的请求数大约等于并发数，单条请求的有效生成速度从约 **50 token/秒掉到 4 token/秒**。184 个输出词在并发 80 时要占大约 **46 秒**。并发乘了 80，完成速度只乘了 **5.2**，中位时延乘了 **16**。这是吞吐已经接近上限时，把更多请求塞进同一批 GPU 的正常表现，不是偶发长尾。

## 1. 实测：时延随并发升高，完成速度升高得慢

| 同时发出 | 成功 / 提交 | 每秒完成 | 中位 / 95 分位 | 四卡生成 token/秒 | 前缀命中 | 功率 | 计算中 / 门口排队 |
|---|---|---|---|---|---|---|---|
| 1 | 189 / 189 | 0.314 | 3.08 秒 / 4.23 秒 | 57.8 | 40.6% | 647 W | 1.15 / 0 |
| 8 | 507 / 507 | 0.840 | 9.62 秒 / 11.37 秒 | 154.5 | 39.5% | 806 W | 7.77 / 0.05 |
| 32 | 761 / 761 | 1.260 | 25.79 秒 / 30.48 秒 | 231.3 | 38.8% | 942 W | 29.8 / 0.59 |
| 80 | 978 / 978 | 1.619 | 50.22 秒 / 60.00 秒 | 296.6 | 38.9% | 1106 W | 73.9 / 2.79 |

相对并发 1：并发 ×80，每秒完成 ×5.15，中位时延 ×16.3，生成速度 ×5.13，预填充速度 ×3.48，功率只 ×1.71。  
95 分位 / 中位大约 1.18–1.37，四档都稳，不是少数请求拖尾。

闭环压测始终保持 N 条在途。Little 定律：在途条数 ≈ 每秒完成 × 平均时延。

| 同时发出 | 每秒完成 × 中位时延 | 每秒完成 × 平均时延 | 计算中 + 门口排队 |
|---|---|---|---|
| 1 | 0.97 | 1.00 | 1.15 |
| 8 | 8.08 | 7.99 | 7.82 |
| 32 | 32.5 | 32.0 | 30.4 |
| 80 | 81.3 | 79.8 | 76.7 |

客户端在途条数就是并发；引擎里看到的条数与之接近。服务把几乎所有在途请求都收进了计算槽位。

## 2. 把 50 秒拆开：门口只占约 1.7 秒

门口排队时间 ≈「门口排队均条数 / 每秒完成」。

| 同时发出 | 门口排队（秒） | 占中位时延 | 进入槽位之后（秒） |
|---|---|---|---|
| 1 | 0 | 0% | 整段都在算 |
| 8 | 0.06 | 0.6% | 9.3 |
| 32 | 0.47 | 1.8% | 23.6 |
| 80 | 1.72 | 3.4% | 45.7 |

每引擎最多 64 个槽位、四引擎共 256 个；并发 80 远用不完。Prometheus 里的「计算中」在并发 80 时平均 73.9，说明请求已经拿到槽位。拿到槽位不等于这一步正在出词——槽位是生命周期占坑，GPU 每一步只吃得下预算以内的预填充块和生成词。

进入槽位之后，单条请求的有效生成速度 = 四卡合计生成 token/秒 ÷ 计算中条数：

| 同时发出 | 有效生成（token/秒/条） | 184 词按此速度要多久 |
|---|---|---|
| 1 | 50.3 | 约 3.7 秒（与整段时延同一量级；单条时预填充和生成串行，分母略偏大） |
| 8 | 19.9 | 9.3 秒 |
| 32 | 7.8 | 23.6 秒 |
| 80 | 4.0 | 45.7 秒 |

并发 8 以上，中位时延几乎等于「在槽位里把 184 个词挤出来的时间」。预填充没有另占一段墙钟，而是和生成抢同一步。

## 3. 从客户端到出词：整条链路

### 3.1 压测客户端

每档保持固定条数在途，完成一条立刻补一条，超时 300 秒。并发 80 时 95 分位 60 秒，没有因超时丢掉请求，也没有在客户端限速。这一层决定了「引擎里始终堆着大约 N 条」。

### 3.2 本机 HTTP

打的是 `127.0.0.1:8500`。网络往返是毫秒级，解释不了从 3 秒到 50 秒。

### 3.3 API 进程（4 个）

`--api-server-count 4` 只负责收 HTTP、把请求交给引擎。本机 **0 失败、0 次限流**。请求全部放进引擎。硅基流动在同一套负载下用 429 挡；Neolink 在并发 32 和 80 用 HTTP 500 挡。自建选择「收下来、做完」，时延就写在成功样本上。

### 3.4 数据并行 4 × 张量并行 1

四张 RTX PRO 6000 是四个独立副本，每张卡装得下整模。一条请求进一张卡，注意力不会拆到四张卡上。并发 80 时大约 **每卡 20 条**。好处是请求级扩容、卡间不用为一条请求做注意力通信；代价是每张卡要独自扛大约 20 条、每条约 3.3 万上下文的 KV，并且用自己的 16384 token 一步预算做混合批。

### 3.5 门口排队（不是主因）

见第 2 节。`--max-num-seqs 64` 没有成为瓶颈。不要把 Grafana 里偶尔出现的 waiting 理解成「50 秒都在排队」。

### 3.6 调度器一步预算（主因）

现网相关参数（`vllm-vlm` 于 2026-09-17 10:19 UTC 拉起，与压测窗口一致）：

- `--max-num-batched-tokens 16384`
- `--max-num-partial-prefills 1`
- `--max-long-partial-prefills 1`
- `--long-prefill-token-threshold 16384`
- `--speculative-config` MTP，推测 2 个 token
- `--gpu-memory-utilization 0.75`，`--kv-cache-dtype fp8`
- `--enable-prefix-caching`

GPU 每一步能吃的 token 数上限是 16384，而且同一步里 **只允许 1 条请求做预填充**。一条新请求现场要算的预填充：

| 同时发出 | 每条现场计算的预填充 token | 其中共享段未命中（约） |
|---|---|---|
| 1 | 27217 | 13863（档内冷启动偏多） |
| 8 | 20586 | 7232 |
| 32 | 19189 | 5835 |
| 80 | 18381 | 5027 |

独特尾巴约 13354 token，按设计打不中缓存。热起来之后每条仍要约 **1.8–1.9 万** 现场计算。一次 16384 的预填充块就会把该卡这一步的预算用完，同卡其它十几条正在生成的请求这一步 **0 个新词**。下一条新请求又来一块。Prometheus 里这些请求仍算「计算中」，只是这一步没排上。

这与调度器示意里「占着槽位、本步没上 GPU」是同一件事。16384 的上限避免了单次 6 万预填充锁死整步数秒，但挡不住「1.8 万 ≈ 一整步」。

### 3.7 预填充算力

四卡合计现场预填充：8548 → 17287 → 24182 → 29756 token/秒，只涨了 3.5 倍。前缀命中稳定在 39–41%（共享段大约 55% 可缓存；聊天接口的 `cached_tokens` 全程为 0，以 Prometheus 为准）。缓存已经在干活，省不下独特尾巴。

### 3.8 生成、KV、推测解码

输出长度四档都是约 184，没有变长。生成是逐步的（MTP 一次最多猜 2 个）。上下文约 3.3 万、并发 80 时单卡约 20 条，每出一词都要读长大 KV。四卡合计生成 58 → 297 token/秒，与每秒完成条数同步，只涨 5.1 倍。单条有效速度 50 → 4 token/秒，直接对应 3 秒 → 46 秒。

功率 647 → 1106 W（×1.71）：并发 1 时单条已经是长预填充，卡并不空；再加并发主要是把步与步之间的空隙填满、提高专家利用率，换不来线性的每条速度。

### 3.9 为什么完成速度只乘 5、时延乘 16

闭环下：每秒完成 ≈ 在途条数 / 单条时延。在途条数被压测钉在 N。单条时延大约随「每卡同时在算的条数」变长。于是 N 变大时，时延几乎同比变长，每秒完成接近封顶。并发 80 仍比 32 高（1.26 → 1.62），还没顶死，但已经远不是线性。

## 4. 同一套请求，两家云端为什么不像这样

| 同时发出 | 自建 每秒完成 / 中位时延 | 硅基流动 | Neolink |
|---|---|---|---|
| 1 | 0.314 / 3.08 秒 | 0.097 / 8.7 秒 | 0.381 / 2.52 秒 |
| 8 | 0.840 / 9.62 秒 | 0.081 / 21.7 秒 | 2.974 / 2.48 秒 |
| 32 | 1.260 / 25.8 秒 | 0.134 / 42.8 秒 | 4.035 / 2.50 秒 |
| 80 | 1.619 / 50.2 秒 | 0.237 / 98.4 秒 | 4.133 / 2.59 秒 |

Neolink 成功样本的中位时延一直约 2.5 秒；并发 32 和 80 分别有 2.0 万、5.2 万次 HTTP 500。它把多余请求拒掉，成功队列里看不到「收进来再做 50 秒」。  
硅基流动用 429 限流，成功每秒完成最高 0.24；放进来的成功样本同样随并发变慢（8.7 → 98 秒）。  
自建 2435 条全部成功：时延是诚实的，没有把慢请求变成错误码。

## 5. 可以排除的原因

- 本机网络、API 进程数、聊天模板
- 思考模式（已关）、输出变长（约 184 未变）
- 前缀缓存失效（命中率四档 39–41%）
- 槽位不够、门口排长队（最多 3.4%）
- 失败重试（0 失败）
- 个别超慢请求（95 分位 / 中位约 1.2）

## 6. 若要压时延，动的是哪一层（未改现网）

现网参数未动。若以后要压中位时延，优先序大致是：

1. **入口限流**：按每卡在途条数收请求，超出返回繁忙。完成速度仍会在每秒约 1.6 条附近，中位时延可以留在数秒到十余秒，而不是 50 秒。和 Neolink 的差别只是：我们用明确的忙、还是用 500。
2. **一步里强制给生成留位置**：在显存允许时提高一步 token 上限，或把长预填充的门槛降低、允许把 1.8 万切成更小块并与生成混步。现在 16384 上限 + 只允许 1 条预填充，长尾巴很容易独占一步。改大上限可能加长单步、也更接近显存墙，需要单独压。
3. **减现场预填充**：缩短独特尾巴，或让产品侧多复用已缓存前缀。缓存已经吃掉共享段的大约四成查询。
4. **加副本**：再加一组四卡，每卡在途条数下降，单条时延会跟着降；完成速度才能继续涨。

「把并发从 80 再往上加」主要换更长的时延，完成速度不会按比例涨。
