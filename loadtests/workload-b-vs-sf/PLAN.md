# 工作负载 B：236 四卡 :8500 vs 硅基流动 Token 账单

只测 **B**（共享前缀、可命中 prefix cache）。  
这份是方案 + 脚本说明，**默认不打流量、不改 :8500、不打 :5180、不花硅基额度**。

构造方式和早上 `direct-llm-80x20m-20260917` 相同（共享前缀 + 独特检索尾巴，cache 大约 40–55%），**长度先定 3 万**。

---

## 1. 为什么只测 B

A（每条独特前缀、cache=0）会把自建打成「每条都全量 prefill」，硅基也按全文输入计费，比的是裸算力，不是我们线上更常见的「同一知识库 / 同一系统提示反复打」。

B 更接近 ViKnow：长上下文里一大段重复，尾巴在变。自建能吃 prefix cache；硅基能不能打折、打多少，要看它回包里的 `cached_tokens`，**不事先假设它和 236 一样**。

硅基是官方 `Qwen/Qwen3.6-35B-A3B`，236 是 FP8。延迟、QPS **不能当同构 serving 冠军赛**，只回答：

> 同样的 B 请求，硅基按牌价要多少钱；236 四卡把这段负载吃下来，摊销 + 电费是多少。

## 4. 硅基会花多少（先估，再跑）

牌价按控制台 CN：**输入 ¥1.80 / M，输出 ¥10.80 / M**。脚本可改。  
若回包带 `prompt_tokens_details.cached_tokens`，按「未命中走 1.80、命中走 `SF_CACHE_CNY_PER_M`」另算一列；没给缓存价就先当 1.80（偏保守）。

单条按 3 万目标 × 早上模板开销 1.10：

```
¥/req ≈ 32965/1e6 × 1.80 + 184/1e6 × 10.80 ≈ 0.0593 + 0.0020 = ¥0.0613
```

QPS 按早上 19k 经验 × 19/30（prefill 更重，请求往少估）。若 QPS 不掉，花费大约再 ×1.6。

| 并发 | 经验 QPS | 约请求数 | 约硅基花费 |
|---|---|---|---|
| 1 | 0.21 | 125 | ¥8 |
| 8 | 0.63 | 380 | ¥23 |
| 32 | 1.27 | 760 | ¥47 |
| 80 | 1.58 | 950 | ¥58 |
| **四档合计** | | **~2200** | **~¥136** |

脚本默认 `SF_BUDGET_CNY=80`，累计估算超了就停当前档。  
建议批准顺序：

1. 只跑 236（不花钱）
2. 硅基 `1,8`（大约 ¥30）
3. 你再说要不要 `32,80`

## 5. 236 四卡怎么折算成 ¥/请求

四卡 RTX PRO 6000 Blackwell，两档购卡口径：

- 低：¥36 万 / 4 卡
- 高：¥44 万 / 4 卡

摊销年限 2 年 / 3 年；日历利用率 30% / 60% / 90%（一天里有多少时间在吃这种负载）。  
电：1.6 / 2.0 / 2.4 kW（4 卡板卡，不含机房空调），电价默认 ¥1.0 / kWh，可改。

```
摊销小时成本 = 购卡 / (年 × 365.25 × 24 × 利用率)
电费小时成本 = kW × 电价
小时成本     = 摊销 + 电
¥/请求       = 小时成本 / (该档实测 QPS × 3600)
```

QPS 是每秒完成数，一小时完成 `QPS × 3600` 条，不能拿小时成本直接除 QPS。

主表固定三列，避免矩阵爆炸：

1. **中位**：36 万 / 3 年 / 60% / 2.0 kW
2. **贵且闲**：44 万 / 2 年 / 30% / 2.4 kW
3. **便宜且满**：36 万 / 3 年 / 90% / 1.6 kW

窗口内再记一列 **实测功率** 的电费（DCGM 4 卡合计），和假设 kW 对照。

例：把早上 2.65 QPS 按 19/30 下调到约 1.68 QPS，中位小时成本仍约 ¥24.8，则 **¥0.0041 / 请求**，硅基约 **¥0.061 / 请求**。DP4 + 3 万现网要以新跑为准。早上 19k 的 demo 表仍可看，不和这次混用。
